## QA-01 실행 접근과 기본 흐름

우선순위 1 / 상태 PENDING

이 Site는 비공개다. 같은 사용자의 승인된 접근 권한으로만 연다. 로그인·권한이 없거나 실행이 막히면 정확한 상태와 필요한 입력을 보고한다. 접근을 우회하거나 다른 사용자의 세션을 사용하지 않는다.

먼저 기존 [정적 QA 기록](../proposals/2026-10-02_qa-baseline-static-review-v1.md)을 읽되, 그 문서의 수동 궁극기·3성·19카드 기대값을 현재 시험에 가져오지 않는다. 문서나 소스를 읽은 것을 실제 플레이 검수로 집계하지 않는다.

실행 체크:
1. 브라우저 종류·버전, 화면 크기, 실제 기기 또는 에뮬레이션 여부, 시작 시각과 확인된 빌드 표시를 기록한다.
2. 첫 화면 → 시작 → 적 이동·처치 → 준비 → 영입 → 첫 중복 갈래 선택 → 보조 카드 선택 → 보스·결과 → 새 런을 확인한다.
3. 안쪽 3×3 배치, 최대 3명, 웨이브 사이 재배치, 경로 한 바퀴 뒤 HP 손실과 퇴장을 확인한다.
4. 경험치와 영입 자원, 카드와 뽑기가 분리되어 있는지 확인한다. 보상 중복·음수 자원·버튼 연타의 중복 처리 여부를 기록한다.
5. 첫 중복이 즉시 승급 1단계와 2갈래 선택을 제공하는지, 같은 런에서 갈래를 바꾸지 못하는지, 이후 중복마다 승급하는지 확인한다.
6. 수동 궁극기 버튼과 그 입력을 요구하는 막힘이 없는지 확인한다.
7. 새 런에서 영웅·승급·갈래·강화·XP·자원이 초기화되는지 확인한다.
8. 최고 웨이브 기록과 재접속을 확인한다. 중간 런 이어하기는 현재 미지원이므로 이어지지 않는 현상을 자동으로 버그 처리하지 않는다.
9. 카드·갈래 선택 창의 입력 관통, 화면 잘림, 버튼 접근과 재시작 후 이전 사건 잔류를 확인한다.

완료 증거:
- 실제 실행한 환경·빌드와 입력 순서가 있다.
- 통과·실패·미검증을 항목별로 나눈다.
- 주요 화면과 실패 재현의 스크린샷 또는 기록이 있다.
- 실패는 기대·실제·최소 재현 단계·영향을 적는다. 관측되지 않은 원인을 단정하지 않는다.
- 비공개 정보가 보이는 스크린샷은 공개 업로드하지 않는다. 공개 승인이 확인된 게임 화면만 사용하고 나머지는 승인된 전달 경로로 인계한다.

접근 차단이면 BLOCKED 기록과 필요한 입력을 남긴 뒤 종속 실행을 멈춘다. 실행 실패를 기능 실패로 바꾸어 집계하지 않는다.

## QA-02 8개 갈래 조합 비교

우선순위 2 / 상태 PENDING / QA-01의 진행 차단 문제 해소 후

비비 2갈래 × 탄코 2갈래 × 로코 2갈래의 8개 조합을 한 번씩 끝까지 확인한다.

| 조합 ID | 비비 | 탄코 | 로코 |
|---|---|---|---|
| C01 | 연사 | 폭발 | 유도 |
| C02 | 연사 | 폭발 | 관통 |
| C03 | 연사 | 소이 | 유도 |
| C04 | 연사 | 소이 | 관통 |
| C05 | 탄막 | 폭발 | 유도 |
| C06 | 탄막 | 폭발 | 관통 |
| C07 | 탄막 | 소이 | 유도 |
| C08 | 탄막 | 소이 | 관통 |

- 동일 빌드와 비교 가능한 배치·영입 순서·카드 예산을 사용한다. 선택과 시드를 고정할 수 없으면 실제 값을 기록한다.
- 정상 플레이에서 목표 조합을 얻지 못하면 미도달 이유와 시도 결과를 기록한다. RNG를 무한 반복하지 말고 필요한 재현용 입력을 두리에게 요청한다.
- 승인된 기존 검수 도구를 사용할 때도 강제 주입·가속·고정 시드 여부를 표시하고 정상 브라우저 플레이 결과와 분리한다.
- 전투·준비·선택 시간, 남은 HP, 처치·누수, 영입·첫 갈래·승급 시점, 선택 카드와 결과를 기록한다.
- 각 완료 런을 체크포인트로 남긴다. 다음 요청에서는 미완료 조합부터 이어가며 완료한 런을 지우거나 반복하지 않는다.
- 재현된 진행 불가, 중복 지급, 잘못된 결과가 나오면 증거를 먼저 보고하고 해당 결과에 의존하는 비교를 중단한다.

완료 증거:
- 8개 조합 각각 실제 결과 또는 명확한 차단 사유가 있다.
- 실제 완료한 조합 수와 미검증 수를 적는다. 차단된 조합을 통과로 계산하지 않는다.
- 8개를 실행하지 못했다면 작업 상태는 DONE 대신 IN_PROGRESS 또는 BLOCKED다.
- 소스/PCK의 기존 40개 기능 시나리오와 이번 브라우저 결과를 구분한다.

## QA-03 화면과 저장 확인

우선순위 3 / 상태 PENDING / QA-01 이후

- 이용 가능한 실제 브라우저에서 좁은 세로·가로 화면을 확인하고 정확한 크기를 기록한다.
- 실제 휴대폰에 승인된 접근이 있을 때만 터치·안전 영역·성능·오디오 시작을 확인한다. 데스크톱 화면 축소를 휴대폰 실기 검수라고 하지 않는다.
- IndexedDB 또는 실제 사용 저장소의 최고 웨이브 기록·새로고침·새 런을 확인한다. 개발자 도구 접근이 없어 구현 저장소를 확인하지 못했으면 관측한 행동만 적는다.
- 전체 계정 데이터 삭제나 권한 확대 없이 확인한다. 저장 초기화가 필요하면 정상 복구 가능한 범위와 승인을 먼저 확인한다.
- 미지원 기능, 접근 차단과 재현된 결함을 구분한다.

## 종료와 보고

새 날짜별 qa 결과 문서에 원본 작업 ID, 상태, 환경·버전, 검수표, 재현·증거, 마지막 완료 지점과 다음 1단계를 적는다. 커밋·파일 링크를 보고한다.

각 “다음” 또는 “ㄱㄱ” 요청에서는 가장 우선인 미완료 작업 하나를 이어간다. 실제 휴대폰이나 파일 접근이 없어도 통과를 추측하지 않는다. 배정 범위가 끝나면 새 테스트를 무한히 추가하지 말고 결과를 두리에게 인계한다.

## 여섯 팀 협업과 의견 보고

2026-10-03 갱신: [공통 협업 규약](2026-10-03-collaboration-protocol.md)을 함께 따른다. 이 절차가 기존의 단순 “한 작업 후 대기” 안내를 보완한다.

- 시작한 승인 작업은 조사·제작·검증·저장·보고까지 진행한다. 사용자가 한정된 배정 묶음을 요청했다면 그 범위를 이어가며, 평범한 단계마다 재확인을 요구하지 않는다.
- 막힌 항목을 기록하고 같은 승인 범위의 독립 작업은 진행한다. 이미 있는 결과와 체크포인트를 재사용하며 새로 시작하지 않는다.
- 결과 끝에 **문제점 / 개선 제안 / 다른 팀 요청 / 다음 작업 후보 1~3개**를 넣는다. 근거·이유·예상 효과·작업량·위험·의존성·현재 규칙과의 충돌을 적고, 다음 후보에는 우선순위와 예상 산출물을 적는다.
- 의견은 제안으로 남긴다. 두리가 채택·보류·사용자 결정 필요를 검토하고 최종 앱을 통합한다.
- 지시서가 없거나 배정이 끝났으면 가장 권장하는 다음 후보를 첫 번째로 제안한다. 사용자가 그 목록을 본 뒤 “ㄱ”, “ㄱㄱ” 또는 “다음”이라고 하면 첫 번째 후보 1개를 시작한다. 새 작업 ID와 승인 범위를 기록한다.
- 후보 승인도 중요한 규칙 변경, 다른 팀 파일 소유, 운영 코드 인계, 새 권한을 자동 허용하지 않는다. 자료 접근 실패를 지시서가 없다는 뜻으로 해석하지 않는다.
