## 결론과 최우선 문제

**QA04-F01 / P1: 처리 활성 상태에서 성급 상점 닫기 실패를 독립 재현했다.**

같은 조건의 Escape 키 이벤트는 닫혔다. 실제 Android Back 입력이 어떤 경로로 전달되는지는 미검증이므로 실제 기기 Back 실패로 확대하지 않는다.

진단 근거: 활성 일반 닫기 시험마다 관측 구간의 닫기 버튼 visibility_changed40회, pressed0회. 정지 대조는 닫힐 때 visibility_changed2회, pressed1회였다. 해당 소스의 화면 갱신에서 비선택 phase의 overlay/닫기 버튼을 먼저 숨긴 뒤 shop_hero 분기에서 다시 표시하는 순서와 일치한다. 화면 요소의 반복 숨김/표시가 눌림을 끊는 기존 메인 재현을 QA가 뒷받침했다. 프레임 수/visibility횟수는 이 시험 환경 관측값이며 기기 FPS 측정이 아니다.

F02 소스 경계: WM_GO_BACK_REQUEST 처리는 gate_open일 때만 있고 상점 경로가 없다. ui_cancel 키 경로는 shop_hero를 처리한다. 키보드 Escape 통과를 Android Back 합격으로 치환하면 안 된다.

초기 시험 보정: root.push_input만 사용한 첫 터치 시험은 정상 정지 대조도 실패했다. 이 결과는 결함 판정에 사용하지 않았다. Input.parse_input_event로 엔진 입력 전달/터치의 마우스 변환을 포함하도록 QA 도구만 보정한 뒤24조건을 재실행했고 정지 대조8개 모두 통과했다. 최초 JSON/로그도 보존했다.

## 최소 재현

1. 위 해시의 v0.3 소스를 격리 실행한다. 초기 배치에서 고철1, 비비 성급 상점을 연다.
2. 화면 처리를 켠 채 '상점 닫기' 중앙을 누른다.
3. 여러 process_frame을 지난 뒤 같은 위치에서 놓는다.
4. 기대: 상점이 닫히고 게임으로 돌아감. 실제: 계속 열림.
5. 고철400에서도 동일. 화면 처리를 정지한 같은 입력은 닫힘.
6. 포커스 OUT/IN 뒤 새 제스처로도 재현. 플랫폼 Back 알림과 Escape 키는 각각 별도 시험한다.

실제 사용자 저장을 지우지 않고 시험 사본만 사용했다. Escape 통과는 기기 우회 방법으로 권고하지 않는다.
