## “다음” 또는 “ㄱㄱ”를 받으면

1. main의 이 안내, 현재 기준 문서, 자기 팀의 최신 승인 지시서를 다시 읽는다.
2. 같은 작업 ID의 결과 문서를 찾아 완료·진행 중·차단 여부를 확인한다.
3. **승인 범위 안에서 가장 우선인 미완료 작업 1개**를 시작하거나 이어간다.
4. 진행 중 기록이 있으면 마지막 검증된 지점에서 이어간다. 원본과 이전 산출물을 지우고 다시 시작하지 않는다.
5. 필요한 파일·권한·결정이 없으면 차단 사유와 필요한 입력을 기록한다. 권한을 우회하거나 결과를 추측하지 않는다.
6. 완료 조건을 만족하면 결과와 증거를 저장하고 해당 작업을 끝낸다. “다음” 한 번으로 새 분야를 계속 확장하지 않는다.
7. 모든 배정 작업이 끝났다면 결과를 요약하고 다음 지시를 기다린다.

이 파일이 존재하거나 GitHub에 새 커밋이 생기는 것만으로 다른 Work가 자동으로 깨어나거나 실행되는 것은 아니다. 사용자가 해당 Work에 이 흐름을 한 번 설정하고 실행을 요청해야 한다. 지시서 공개와 실제 착수·인수는 구분한다.

“당신은 밤길 원정대의 [기획/디자인/음향/QA] 담당입니다. 앞으로 내가 ‘다음’ 또는 ‘ㄱㄱ’라고 하면 https://github.com/oh4789/good-game/blob/main/docs/WORK_START_HERE.md 를 읽고, 현재 기준과 자기 팀 지시서 및 기존 결과를 확인하세요. 승인된 미완료 작업 중 우선순위가 가장 높은 1개를 이어가세요. 기존 파일과 다른 팀 작업은 덮어쓰지 말고, 실제 산출물과 검증 결과를 새 날짜별 문서에 남긴 뒤 커밋·파일 링크를 보고하세요. 게임의 중요한 방향 변경은 제안으로 남기고 두리에게 통합을 맡기세요.”

이 문구는 사용자가 해당 Work에 전달할 설정용 문구다. 저장소에서 읽었다는 이유만으로 별도 계정·도구·공개 업로드 권한까지 생기지는 않는다.

## 상태와 결과 저장 규칙

지시서의 PENDING은 발행 당시 미착수 상태다. 여러 팀이 같은 상태 파일을 고치지 않도록 지시서는 그대로 두고, 각 팀이 새 결과 문서로 상태를 남긴다. 상태는 PENDING, IN_PROGRESS, BLOCKED, DONE 중 하나를 사용한다. DONE은 해당 지시서의 완료 증거가 있을 때만 쓴다.

결과 파일명: `docs/proposals/YYYY-MM-DD_<team>_<task-id>_<subject>.md`

- 팀 접두사는 planning, design, audio, qa 중 하나를 쓴다.
- 같은 경로가 있으면 내용을 읽고 새 `_v2` 또는 `_v3` 파일로 추가한다.
- 원본 작업 ID, 지시서 링크, 확인한 기준 문서와 소스 버전, 상태를 적는다.
- 한 일, 실제 산출물, 검수 방법과 결과, 남은 일과 차단 사유를 짧게 적는다.
- 진행 중이면 마지막 완료 지점과 다음 1단계를 적어 재실행 때 중복 작업을 막는다.
- 결과 커밋 뒤 사용자에게 커밋 해시·링크와 파일 링크를 보낸다. 자기 커밋 해시를 파일 안에 넣으려고 재귀적으로 수정하지 않는다.
- 두리는 결과 기록을 읽고 통합 여부와 다음 날짜의 지시서를 정리한다. 결과 문서만으로 게임 반영 완료를 선언하지 않는다.

## 범위와 공개 자료 주의사항

- 영웅 3종의 6갈래, 수동 궁극기 없음, 첫 중복 즉시 승급, 이후 중복마다 성장, 런 한정 보유를 유지한다.
- 6영웅·18빌드·54카드 확장은 아직 후속 제안이다.
- 뽑기 비용과 승급 계수 등은 임시 구현 수치다. 비교 근거 없이 영구 확정하거나 자동으로 바꾸지 않는다.
- 자기 팀의 새 문서·산출물만 만든다. 다른 팀 문서, 공용 코드, 기존 원본을 덮어쓰지 않는다.
- 이 저장소는 공개다. 개인정보, 비공개 대화 링크, 인증 정보, API 키, 비공개 업무 자료를 올리지 않는다.
- 게임용 기획 자료의 공개 정리와 에셋 바이너리의 공개 업로드 권한은 구분한다. 에셋은 공개 승인이 있고 사용 권리를 확인한 것만 공개한다. 불분명하면 파일명·해시·검수 상태만 문서화하고 실제 파일은 승인된 전달 경로로 인계한다.
- 확인하지 않은 이미지·음원·플레이를 검수 완료로 표시하지 않는다.
