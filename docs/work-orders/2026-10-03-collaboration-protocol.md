# 여섯 Work 팀 협업과 인계 규약

- 발행일: 2026-10-03 UTC
- 발행·통합 담당: 두리
- 대상: 기획, 디자인, 음향, QA, 개발1, 개발2
- 적용 상태: 현재 협업 절차
- 게임 규칙: [v0.3 현재 기준](../proposals/2026-10-03_v03-canonical-decisions.md) 유지

사용자는 여섯 팀이 제작과 의견 제시를 함께 하고, 두리가 최종 앱 구현·통합·검수·배포를 맡는 방향을 정했다. 중요한 게임 방향은 사용자가 최종 결정한다. 이 규약은 작업 방식과 인계 범위를 정하며, 새로운 게임 규칙을 승인하지 않는다.

이 규약은 이전 문서와 Work 설정의 단순 “배정 완료 후 대기” 문구를 대체한다. 배정이 끝나면 다음 후보를 먼저 제안하고, 사용자가 그 목록 뒤 시작을 요청하면 첫 후보 1개를 진행한다. 인증·공개 범위·파일 소유·중요한 규칙 변경의 승인 조건은 대체하지 않는다.

## 1. 한 번 요청하면 어디까지 진행하는가

“다음” 또는 “ㄱㄱ”는 자기 팀의 승인된 미완료 작업 중 가장 우선인 항목을 시작하거나 이어가라는 뜻이다. 시작한 작업은 필요한 조사 → 제작 → 검증 → 저장 → 보고까지 진행한다. 이 범위 안의 평범한 단계마다 다시 “진행할까요?”라고 묻지 않는다.

사용자가 “이번 지시서의 배정 작업을 끝까지 진행해줘”처럼 작업 묶음을 명시했다면 그 범위가 우선한다. 해당 팀 지시서에 이미 배정된 항목을 순서대로 진행한다. 반복 작업, 무관한 새 분야, 미승인 확장까지 허용한 것으로 해석하지 않는다.

- 완료 기록이 있으면 다시 만들지 말고 실제 완료 조건과 증거부터 확인한다. 작업 ID가 없더라도 내용이 같은 선행 산출물을 재사용한다.
- 진행 중 기록은 마지막 완료 지점에서 이어간다. 기존 파일·이전 결과를 지우고 시작하지 않는다.
- 막힌 항목은 필요한 파일·접근·결정을 정확히 적고, 같은 승인 묶음 안에서 독립적으로 가능한 다음 항목을 진행한다.
- 다른 배정 항목도 같은 입력에 의존하면 차단을 보고한다. 별도로 제안할 수 있는 유용한 독립 작업이 있으면 다음 후보로 제시하고 사용자의 시작 요청을 기다린다. 자료를 추측하거나 의미 없는 문서를 늘리지 않는다.
- 새 권한, 비용, 공개 범위 변경, 중요한 규칙 변경이 필요하면 해당 부분을 멈추고 확인한다.
- 배정 범위의 검증·저장·보고가 끝나면 종료한다. 다음 작업 후보는 제안으로 남기며, 아래 절차에 따른 사용자의 시작 요청 전에는 실행하지 않는다.

GitHub 문서 게시만으로 Work가 자동으로 실행되지는 않는다. 사용자가 해당 Work에서 지시서를 읽고 작업하도록 시작해야 한다.

## “쭉해줘”라고 요청하면

“쭉해줘”는 현재 승인된 목표나 명시한 작업 묶음을 깊이 있게 끝까지 진행하라는 요청이다. “ㄱ/다음”으로 다음 후보 하나를 시작하는 흐름과 구분한다.

- 자기 역할과 승인 범위에서 조사 → 구현·제작 → 테스트 → 발견한 문제 수정 → 재검증 → 통합 인계까지 이어간다. 두리는 최종 앱 통합과 배포 검수까지 맡는다.
- 작은 단계 하나를 끝냈다는 이유로 중간에 멈추지 않는다. 목표 완성에 필요한 후속 작업을 발견하면 기존 승인 범위 안에서 함께 처리한다.
- 오래 걸린 모양을 만들기보다 완성도와 검증 깊이를 높인다. 불필요한 반복·문서·테스트를 늘리지 않는다.
- 중요한 결과와 차단은 보고하면서 진행한다. 중대한 방향 변경, 새 권한·비용·공개 범위 또는 다른 팀 소유 파일의 인계가 필요하면 그 부분은 확인한다.
- 목표와 배정 범위가 완료되거나, 남은 일이 필요한 입력·권한에 막히면 결과와 다음 판단을 남긴다. 사용자 취소·범위 변경을 즉시 따른다.

향후 실제 기능 파일을 Work에 맡길 때에는 두리가 작업 ID, 정확한 파일 경로, 기준 커밋, 격리 브랜치, 허용 변경, 인수 조건을 지정한다. 한 파일에는 한 명의 변경 담당만 둔다. 다른 담당의 수정이 필요하면 요청으로 남기고 인계가 확인된 뒤 작업한다.

## 3. 소스 접근과 공개 경계

공개 `good-game` 저장소는 현재 문서 자료실이다. 문서를 읽거나 Site 주소를 안다는 사실은 게임 소스를 인수했다는 증거가 아니다.

개발1·2는 같은 사용자가 승인한 Library 또는 소스 전달물에서 실제 파일을 열고 버전·해시·실행법을 확인해야 한다. 접근할 수 없으면 필요한 소스 버전과 파일 종류를 적고 차단 상태로 보고한다. 아직 받지 않은 코드의 경로나 API를 상상해 “구현 완료”로 표시하지 않는다.

- 확인된 같은 사용자 Library 전달물: `Nightroad-Square-Defense-v0.3-SOURCE.zip`. 접근 가능한 Library 도구로 찾아 실제 파일을 확인한다. 사용할 수 없으면 이 파일의 첨부가 필요하다고 보고한다. 공개 문서에는 비공개 Library 링크를 넣지 않는다.
- 현재 안정 기준 소스: `922f0808783aa31a88395a80c877e71bce7f0edc`
- 현재 배포 기준: `11a9a0a43af37888e6489167e8fb1fc7173fb0f1`
- 다른 소스를 받았다면 차이를 보고하고 해당 작업의 기준을 확인한다.
- 소스·패치·에셋 전달은 승인된 같은 사용자 경로를 사용한다. 비공개 게임 코드를 이 공개 저장소에 자동으로 올리지 않는다.
- 공개 결과에는 비공개 대화 링크, 인증 정보, 개인정보, 비공개 소스 내용을 넣지 않는다.
- 인증 거절을 우회하거나 되풀이하지 않는다. QA의 기존 로그인 차단을 게임 결함으로 바꾸어 보고하지 않는다.

## 5. 모든 팀의 완료 보고 양식

각 결과 문서 마지막에 다음 내용을 포함한다. 새로운 의견이 없으면 “추가 없음”이라고 적는다. 이미 보고한 같은 문제는 링크로 연결한다.

### 작업 결과

- 작업 ID, 담당 팀, 상태
- 기준 소스·문서 버전과 실제 사용 환경
- 재사용한 선행 결과, 이번에 바꾼 부분
- 실제 산출물과 승인된 인계 상태
- 실행한 검증, 통과·실패·미검증, 증거
- 마지막 완료 지점, 남은 일과 차단 입력

### 문제점

각 문제에 근거·재현 방법, 원인 또는 아직 확인되지 않은 점, 영향, 현재 규칙과의 충돌 여부를 적는다. 관측 사실과 추정을 구분한다.

### 개선 제안

각 제안에 이유, 예상 효과, 대략적인 작업량, 위험, 의존하는 팀·자료, 현재 규칙과의 충돌 여부를 적는다. 상태는 **제안**이다. 의견을 냈다는 이유로 게임에 자동 적용하지 않는다.

### 다른 팀 요청

받을 팀, 필요한 파일·정보·검수, 필요한 이유, 해당 입력이 막고 있는 작업 ID를 구체적으로 적는다. 위임된 파일 변경 권한 없이 다른 팀 파일을 수정하지 않는다. 저장소에 요청을 적은 것을 상대방의 수락으로 간주하지 않는다.

### 다음 작업 후보 1~3개

각 후보에 우선순위, 지금 필요한 이유, 예상 산출물, 의존성·차단 요인을 적는다. 위의 개선 제안과 겹치면 같은 제안 ID를 사용한다. 두리가 중복·충돌·필요성을 검토할 수 있도록 기록한다. 사용자가 후보를 보고 ‘ㄱ’, ‘ㄱㄱ’ 또는 ‘다음’으로 시작을 요청하면 아래 절차를 적용한다.

## 6. 지시서가 없거나 배정 작업이 끝났을 때

1. 최신 확인 가능한 기준과 기존 결과를 읽고 자기 팀의 다음 작업 후보 1~3개를 제안한다. 가장 권장하는 후보를 첫 번째에 둔다.
2. 각 후보에 범위, 이유, 예상 산출물, 완료 조건과 의존성을 적는다. 이 단계의 상태는 제안이다.
3. 사용자가 그 목록을 본 뒤 “ㄱ”, “ㄱㄱ” 또는 “다음”이라고 하면 **직전에 제안한 첫 번째 후보 1개**를 시작한다. 다른 번호를 명시하면 그 후보를 따른다. 세 후보 전체 실행으로 해석하지 않는다.
4. 시작할 때 팀별 새 작업 ID를 붙이고 해당 후보와 사용자의 시작 승인 시점·범위를 결과 기록에 남긴다. 공개 문서에 비공개 대화 원문이나 링크를 넣지 않는다.
5. 자기 역할과 현재 승인된 게임 규칙 안의 작은 독립 작업은 조사·제작·검증·저장·보고까지 이어간다.
6. 규칙 변경, 다른 팀 소유 파일, 운영 코드 인계, 새 접근·비용·공개 권한이 필요하면 그 부분은 두리 또는 사용자 확인을 거친다. “다음”으로 이런 경계를 우회하지 않는다.
7. 저장소나 자료에 접근하지 못한 상태를 “지시서 없음”으로 단정하지 않는다. 확인한 마지막 맥락과 불확실성을 표시하고, 필수 자료가 없으면 그것을 요청한다.

QA의 로그인 차단이 독립적인 기획·자료 정리까지 모두 막는 것은 아니다. 확인된 자료로 가능한 범위만 제안한다. 실제로 유용한 후보가 없으면 그 이유와 필요한 입력을 설명한다.

현재 지시서가 존재하고 미완료 배정이 있으면 그 작업을 우선한다. 기존 작업이 끝났거나 명시적으로 보류된 경우에 이 후보 절차를 사용한다. 다음 후보 승인 후에도 최종 앱 통합·검수·배포는 두리가 맡는다.

## 7. 두리의 검토와 다음 지시

두리는 결과를 읽고 제안을 **채택**, **보류**, **사용자 결정 필요**로 구분해 새 날짜별 검토 기록에 남긴다. 기록에는 제안 ID·근거·선택 이유·담당·다음 작업 또는 필요한 결정을 적는다.

채택되더라도 실제 코드 반영·검증·배포 완료는 각각 별도로 확인한다. 현재 승인 범위를 벗어나는 중요한 방향은 사용자에게 묻는다. 개발팀의 결과는 두리가 검토하고 최종 앱에 통합한다.

## 8. 저장과 인계

- 새 결과는 `docs/proposals/YYYY-MM-DD_<team>_<task-id>_<subject>.md`로 추가한다.
- 팀 접두사는 planning, design, audio, qa, development1, development2다.
- 기존 결과는 덮어쓰지 않는다. 후속 기록은 새 버전 파일로 연결한다.
- 지시서의 PENDING은 발행 시점 상태다. 현재 진행 상태는 작업 ID의 최신 결과 기록으로 확인한다.
- 개발 산출물에는 기준 버전, 변경 경로 목록, diff 또는 소스 묶음, 실행 명령, 테스트 결과, 남은 한계를 함께 제공한다. 비공개 코드가 포함된 전달물은 승인된 비공개 경로를 쓴다.
- 저장 후 커밋·파일 링크와 짧은 결과를 보고한다. 같은 커밋의 해시를 자기 파일 안에 넣기 위한 반복 수정은 하지 않는다.
