## 1. 읽는 순서와 기준 경계

[Work 시작 안내](../WORK_START_HERE.md), [현재 구현 이력](../CURRENT_IMPLEMENTATION.md), [메인 설계 인수](2026-10-04_main-design-growth-intake.md), [RS-01 유물 제안](2026-10-04_relic-combo_RS-01_core-relic-barricade-framework.md)을 먼저 읽는다.

기존 문서의 “유물 미구현·3성 잠금”은 당시 배포/후보의 이력이다. 아래에는 **현재 별도 후보에서 구현하고 검증한 내용**을 기록한다. 이 후보를 기존 배포에 이미 포함됐다고 해석하지 않는다.

- 추천 실험 기준은 v0.4.2를 유지한다.
- 선택형 배포 v0.4.5도 이번 문서 작성으로 변경하지 않는다.
- v0.4.6은 APK 패키징 중이다. 최종 APK 확인·게시·실제 설치를 완료했다고 쓰지 않는다.
- 후보 상태는 메인이 인수한 최신 검증 보고를 기준으로 한다. 이 문서 작성 과정에서 게임 시험을 다시 실행한 것은 아니다.
- 공개 저장소는 문서 자료실이다. 비공개 소스·에셋·실행 링크·Library ID·인증 정보는 싣지 않는다. 팀은 승인된 별도 전달 경로에서 정확한 후보를 받아 버전을 대조한다.

## 2. 유지할 결정과 판단 기준

1. **1성도 유효한 선택지로 남긴다.** 1성 물량·1성 능력 투자·2성 집중·3성 완성·혼합은 서로 다른 운영을 요구해야 한다.
2. 합성이 언제나 자동 정답이 되도록 만들지 않는다. 이미 산 성급 전용 능력, 합성 시점, 칸 확보, 유물 조건과 사거리의 기회비용을 함께 본다.
3. 자동 시험의 성공은 계약·회귀 검증의 증거다. 사람의 재미, 실제 폰 조작, 가독성·청취·성능 합격과 구분한다.
4. 메인은 최종 앱 통합과 배포를 소유한다. 팀은 승인된 담당 범위의 증거·격리 산출물을 인계하고 같은 운영 파일을 동시에 덮어쓰지 않는다.
5. 기존 문서를 고쳐 과거 상태를 지우지 않는다. 변경 결정과 후속 증거는 날짜·주제가 있는 새 문서로 연결한다.

## 3. 이번 후보에 실제 포함된 유물

첫 후보는 유물 3종이다. 원정당 1개를 고르며, 처치 24회 뒤 해금하고 고철 12로 직접 선택한다. RS-01의 “웨이브 3 무료 선택”이나 12종 전체 구현을 뜻하지 않는다.

| 유물 유형 | 후보 규칙 | 운영상 확인할 점 |
|---|---|---|
| 1성 군단 | 다른 1성 1명당 8%, 최대 40% 보너스 | 합성을 미루고 1성 수를 유지하는 선택이 실제로 의미 있는가 |
| 소수 정예 | 부대 4명 이하에서 35% 보너스 | 적은 수의 고성급 집중과 칸·구매 선택의 비용이 드러나는가 |
| 고립 배치 | 상하좌우 인접 유닛이 없을 때 위력 +15%, 사거리 +40 | 대각선과 직교 인접을 혼동하지 않고 실제 공격 가능 구간을 읽을 수 있는가 |

소수 정예의 성급 범위는 런 규칙 버전별로 구분한다.

- 기존 v4 규칙 런: 기존 2성 적용 의미를 유지한다.
- 새 v5 규칙 런: 2성과 3성에 적용한다.
- 앱 표시 버전 v0.4.6과 런 규칙 v5는 서로 다른 식별자다. 예전 런에 새 의미를 조용히 덮어씌우지 않는다.

## 4. 이번 후보에 실제 포함된 3성

- 같은 영웅의 2성 3명을 합쳐 3성 1명을 만든다.
- 선택한 생존 유닛의 ID·칸·갈래를 유지한다. 재료는 서로 다른 갈래를 섞을 수 있다.
- 1성·2성 전용 구매 기록은 각 성급에 보존하며 3성에 자동 승계하지 않는다. 기존 성급 투자 기록을 삭제하거나 공짜로 이전하는 규칙이 아니다.
- 3성 전용 카드 18종이 포함된다.
- 3성 기본 배율 **4.40은 실험값**이다. 최종 밸런스 확정이나 모든 상황의 우월함을 뜻하지 않는다.

### 여섯 갈래 완성 효과

| 영웅 | 갈래 | 후보의 완성 효과 |
|---|---|---|

## 5. 저장·합성·미리보기 검증 범위

현재 후보에서는 다음 경계를 보강했다.

- v2/v3/v4 이전 저장을 v5 후보에서 읽는 마이그레이션 경로.
- 여러 차례 합성 중 이미 발사된 공격의 소유권 연결.
- 실제 편성과 공통 계산을 사용하는 미리보기.
- 잘못된 자료형이 포함된 저장 데이터의 검증 강화.

팀은 “새 후보에서 읽었다”와 “기존 런의 의미를 새 규칙으로 바꿨다”를 구분한다. 저장/복원 전후 ID·칸·갈래·구매 기록·진행 중 공격·RNG·열린 선택을 대조하고, 손상 입력 처리와 정상 저장 보존을 별도로 기록한다.

## 6. 인수한 검증 증거와 한계

| 증거 묶음 | 인수 결과 | 해석 경계 |
|---|---|---|

검사 수는 실행 범위를 설명하는 보조 정보다. APK 자체 검증과 실제 기기 인수는 별개이며 아직 완료로 합산하지 않는다.

### 밸런스 관측

- 스크립트로 자연 진행한 72런은 모두 클리어했고 종료 HP는 20이었다.
- 해당 관측에서 3성 완성은 웨이브 9~10으로 늦었다.
- 동일한 9명분 복사 수를 비교한 장면에서는 2성 카드 투자가 큰 경우 3성 쪽 피해가 더 낮은 사례가 자주 나타났다.

따라서 “3성은 무조건 약하다”, “언제나 합치는 것이 최선이다”, “모든 빌드가 최종 합격했다” 어느 쪽도 확정하지 않는다. 복사 수가 같아도 고철 지출·구매 기록·배치·도달 시각까지 같다는 뜻은 아니다. 제한된 자동 정책의 무누수 클리어는 사람의 난이도나 선택 재미를 대신하지 못한다.

## 7. 팀별 다음 지시

이 문서는 팀이 바로 착수할 수 있도록 범위·증거·완료 조건을 제공한다. 문서 게시 자체가 다른 Work를 실행하거나 외부 에이전트에 연락하는 행위는 아니다. 기존에 완료된 작업은 반복하지 않는다.

### QA — 실제 Android 인수: OPEN

**첫 단계:** 메인에서 최종 APK의 버전·패키지·서명·파일 식별이 확인된 뒤 실제 기기 시험을 시작한다. APK가 아직 없으면 체크리스트와 기존 진행 보존 준비까지만 한다.

- 같은 앱 업데이트 및 필요한 신규 설치 경로를 구분한다. 기존 진행을 지우는 삭제·초기화를 기본 절차로 요구하지 않는다.
- Continue, 진행 중 선택창, 합성 취소/확정, 3성 전후 저장, 배경 전환·복귀를 확인한다.
- 실제 touch/드래그/Back, 여러 프레임에 걸친 press→release, 작은 화면에서 고정 요약과 버튼 접근성을 검사한다.
- 스피커 출력, 음소거·중단·복귀, 장시간 프레임 저하·발열을 관측한다.
- 기기/OS/앱 버전, 재현 순서, 기대/실제 결과, 화면 또는 로그 증거와 미실행 범위를 남긴다.

**완료 조건:** 실제 수행 항목만 PASS/FAIL로 판정하고 미실행은 OPEN 또는 BLOCKED로 남긴 인수표. 자동 네이티브 PASS로 기기 항목을 닫지 않는다.

### 디자인 — 여섯 3성 효과의 실제 전투 가독성: PENDING

**첫 단계:** 위 여섯 갈래를 실제 후보 전투 화면에서 하나씩 관측하고 2성 대비 무엇이 달라 보이는지 기록한다.

- 잔불/관통/추가 폭발/화염 커튼/파편/끝점 폭발을 실제 공격 시점·표적·범위와 대조한다.
- 적 HP·전장·선택 표시가 이펙트에 가려지는지, 고배속과 작은 화면에서 구별되는지 검사한다.
- 정적 시안과 현재 게임 캡처를 분리한다. 존재하지 않는 원화·애니메이션을 구현 완료로 표기하지 않는다.
- 각 문제에 최소 변경안, 기대 효과, 비용·위험과 실제 전투 재검증 방법을 적는다.

**완료 조건:** 6갈래 모두 증거와 판정이 있고, 구현된 표현/제안 표현/미검증 표현을 구분한 보고.

### 밸런스·기획 — 같은 지출의 성급별 선택 비교: PENDING

**첫 단계:** 동일 시드·고철 지출·비교 시각·영웅 구성 조건을 고정하고 1성 유지, 2성 유지, 3성 승급, 혼합을 비교한다.

- 여러 시드와 세 유물 조건을 포함한다. 1성/2성 전용 카드 투자 후 합성의 기회비용도 계산한다.
- 총피해만 보지 말고 실제 공격 가능 시간, 사거리 도달, 처치 지연, 누수, 완성 시점, 칸 확보를 기록한다.
- 3성을 얻기 전 웨이브와 얻은 뒤 웨이브를 나눈다. 늦은 도달을 완성 효과의 약함으로 혼동하지 않는다.
- 자동 정책과 사람의 선택 이유·이해도 관측을 분리한다. 사람이 합성을 보류하거나 1성을 남긴 이유를 받는다.
- 4.40 조정, 유물 수치 변경, 3성 도달 시점 변경은 비교 자료를 붙인 **제안**으로 제출한다.

**완료 조건:** 조건이 명시된 비교표, 유리/불리한 상황, 1성 생존 가능성과 빌드 차이에 대한 관측, 후속 후보 1~3개. 모든 전략을 같은 숫자로 평준화하거나 합성을 무조건 최선으로 만드는 결론을 기본값으로 삼지 않는다.

### 개발 — 최종 패키지 게이트와 결정 기록: IN_PROGRESS

**첫 단계:** 메인 패키징 결과와 정확한 APK 식별을 연결하고 소스/PCK 결과를 APK 결과로 잘못 표시하지 않는다.

- 최종 APK 안의 런타임이 검증 후보와 일치하는지 확인한다.
- 새 v5 런과 이전 v4 런의 소수 정예 적용 범위, 저장 마이그레이션, 다단 합성 공격 소유권, 미리보기/실제 효과 동일성을 재확인한다.
- 마지막 변경이 헤더뿐인지와 그 게이트의 범위를 기록한다. 기능 변경이 생기면 영향 범위 검증을 다시 연결한다.
- 변경 경로·기준 버전·실행 방법·실패/수정/재검증을 기록하고 운영 파일과 게시 작업은 두리에게 인계한다.

**완료 조건:** 정확한 최종 패키지의 검사 영수증과 배포 전 남은 문턱 목록. APK 생성, 검증, 게시, 다운로드, 설치, 실기기 인수를 각각 분리한다.

### 음향 — 실제 기기 청취 연계: PENDING

QA 기기 시험과 연결해 공격 밀집 시 중요 신호의 구별, 합성·승패·누수 신호, 음소거·배경 복귀를 듣고 기록한다. 코드상의 음향 이벤트 발생을 실제 청취 합격으로 바꾸지 않는다. 새 사운드 제작은 확인한 문제와 승인된 범위에 맞춘 별도 제안으로 남긴다.

## 8. 모든 팀의 보고 형식

각 결과에는 아래 항목을 빠짐없이 포함한다.

1. 작업 ID·상태·기준 버전과 정확한 대상.
2. 실제 산출물, 수행한 검증, 증거와 제한.
3. 완료한 일과 남은 일을 분리한 목록.
4. 문제점: 재현·영향·확실한 사실·미확인 부분.
5. 의견과 개선 제안: 이유·예상 효과·비용·위험·다른 팀 의존성.
6. 다음 후보 1~3개: 권장 순서, 범위, 산출물, 완료 조건.
7. 마지막 완료 지점과 바로 이어갈 다음 한 단계.

상태는 PENDING / IN_PROGRESS / BLOCKED / DONE을 쓴다. 증거가 있어야 DONE이다. 두리는 의견을 채택 / 보류 / 사용자 결정 필요로 정리한다. 보고를 받았다는 사실과 앱 반영·배포 완료를 혼동하지 않는다.

파일은 `docs/proposals/YYYY-MM-DD_<team>_<task-id>_<subject>.md`에 새로 추가한다. 이미 있으면 내용을 읽고 새 접미사를 사용한다. 저장 후 커밋·파일 링크를 보고한다.
