## 결론

HP 0 패배에서 장판·포탄이 내부 상태에 남는 관측은 현재 소스에서도 재현됐다. 그러나 검사한 조건에서는 추가 피해·추가 음향 사건·전투 재개·새 원정 오염이 없었다. 따라서 전투 결함으로 분류하거나 긴급 정리 패치를 적용할 근거는 없다. 현재 상태를 보존하고 1차 인수표의 남은 검수에 집중하는 것을 권장한다.

## 실행 결과

승급 1/2 × 패배 경로 3종, 총 6개 고정 fixture와 180개 assertion이 통과했다.

| 종료 경로 | 종료 HP | 남은 장판/포탄/효과 | 종료 후 피해 |
|---|---:|---|---:|
| 다른 적이 남은 HP 0 패배 | 0 | 1 / 1 / 2 | 0 |
| 마지막 적 누수로 HP 0 패배 | 0 | 1 / 1 / 2 | 0 |
| HP 강화 후 보스 유출·미처치 패배 | 2 | 0 / 0 / 0 | 0 |

승급 1과 2에서 동일한 잔존 개수를 관측했다. HP 0 경로는 종료 분기에서 즉시 반환하며, 보스 미처치 경로는 웨이브 정리 뒤 종료되므로 차이가 난다.

확인한 항목:
- 실제 공격/포탄 API로 장판 1개와 비행 중 포탄 1개를 만들고 누수로 패배시켰다.
- 종료 후 1·3·10배 모델 입력 각각 120회(dt 0.25)를 넣어 전체 저장 대상 상태가 변하지 않음을 확인했다. 10배는 모델 방어 확인용이며 일반 UI에서 제공된다는 뜻이 아니다.
- 패배 사건은 1회, 종료 이후 추가 모델 음향 사건은 0회였다. 실제 스피커 청취나 음향 voice 검증은 아니다.
- 패배 상태의 검증·실제 파일 저장·새 Store 읽기·새 모델 복원 후 상태 바이트가 일치했다. 복원 뒤에도 피해와 시간이 진행하지 않았다.
- 패배 상태에서 start_wave가 거부됐다.
- 새 원정에서 장판·포탄·효과와 진행이 초기화되고, 저장 본문과 백업 모두 새 상태로 교체됐다.
- 새 원정은 같은 seed의 새 모델과 게임 진행이 같고, 이전 입력의 중복 적용을 막는 reward_epoch/recruit_seq/promotion_epoch만 각각 1씩 증가했다.

## 초기 검사 보정

첫 실행 162검사 중 6개가 실패했다. 도구가 새 원정의 전체 바이트를 새 객체와 같다고 가정했기 때문이다. 소스 확인 결과 세 입력 식별자가 reset 때 증가하는 의도된 동작이었다. 그 증가를 각각 검사하고 나머지 진행을 비교하도록 도구만 보정해 180검사를 통과했다. 초기 결과는 initial-results.json에 보존한다. 초기 행의 reset_equals_fresh는 당시 고정 표시였으므로 합격 근거가 아니며, 실패 목록이 우선한다. 최종 판정은 results.json을 따른다.

## 화면 영향과 한계

SquareScreen 소스 검토에서는 종료 상태에서 전투 field와 battle_foreground를 숨기며, 저장된 종료 원정은 '결과 보기'로 안내한다. 이는 정적 확인이며 이번에 화면 렌더링·버튼 조작을 실행한 증거가 아니다. 결과 보드의 모든 시각 요소·APK 실제 표시·브라우저·IndexedDB·기기 청취는 미검증으로 둔다.

fixture에는 탄코 소유·승급·갈래, 큰 표적 HP와 정지 속도, 경로 끝의 누수 적, 후속 공격 차단 쿨다운, 스폰 중단이 포함된다. 보스 경로에는 실제 보스 적과 공용 HP 카드 1회를 설정했다. 자연 플레이·승률 결과가 아니다.

## 문제점 / 개선 제안

- 과거 잔존 관측은 확인됐지만, 이번 범위의 기능 결함은 재현되지 않았다.
